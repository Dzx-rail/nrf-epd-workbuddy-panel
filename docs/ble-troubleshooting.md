# BLE 故障排查（以 Windows 为主）

这类故障极容易被误判成代码 bug。按下面的顺序排查，命中率从高到低。

## 1. 先量广告间隔，再谈其他

设备静止、电量充足却频繁连不上时，第一件事是测广播频率：

```python
# 30 秒内收到的广播次数 / 30 = 平均间隔
async with BleakScanner(detection_callback=cb) as scanner:
    await asyncio.sleep(30)
```

- 正常：**1~2 秒一次**
- 异常：**6 秒一次** → 设备进入省电广播模式

6 秒间隔意味着连接请求要等下一轮广播才能送达，实测建链耗时 20~40 秒，
期间 Windows 会主动取消（`WinError -2147023673`，即 `E_ABORT`）。此时报错信息与「设备不存在」完全不同，
但结果一样是失败。

对照物很关键：同场再抓一个同类设备做基线，若它 1.4 秒、目标 6 秒，即可定性。

## 2. 六类典型故障

| 现象 | 判定 | 处置 |
| --- | --- | --- |
| 扫描不到目标，但其他设备正常 | 设备休眠或已下电 | 按复位键唤醒；确认电池 |
| 广播正常，连接在 1~2 秒内被取消 | Windows 残留半开链路 | 关闭再开启蓝牙适配器（约 9 秒），或重启 `bthserv` |
| 连接耗时 20 秒以上才成功 | 慢速广播 / 链路临界 | 放宽客户端超时到 90 秒；优先用扫描命中后立即连接 |
| 连续多次成功率为 0，重置适配器后又好了 | 每轮连接后未彻底拆除 | 断开后等待 5 秒再退出进程 |
| 设备时隐时现 | 广播稀疏 + 扫描窗口太短 | 扫描预算 ≥40 秒 |
| 多块标签时推错屏 | 按名称前缀取第一个 | 必须按 MAC 锁定，且**禁止回退到其他设备** |

## 3. Windows 特有的两个坑

**`BleakScanner.find_device_by_filter` 不可靠。** 名称在首个广播包里往往尚未解析，
过滤条件直接不命中。改用常驻 scanner 轮询 `discovered_devices_and_advertisement_data`，
命中后关闭 scanner 再连接。

**`SO_REUSEADDR` 会破坏单实例互斥。** 与 Linux 语义相反，Windows 上它允许重复绑定同一端口，
于是「端口占用即视为已有实例」的判断失效，会出现两个守护进程互相抢锁、争抢 BLE 连接。
用端口做互斥时**不要**设置该选项。

## 4. 进程被环境回收

以工具方式（`Start-Process` 等）拉起的后台进程，常在同一会话结束时被回收。
要真正常驻，需由**用户会话自身**启动：启动文件夹放 `.cmd`、登录项、或系统服务。
判断依据是重启后 `Get-CimInstance Win32_Process` 里能否看到该进程。

## 5. 不要做的两件事

- **不要为「连不上」加更多重试次数来掩盖问题。** 先定位是广播、链路还是残留连接，重试只能缓解最后一类。
- **不要在检测到多块设备时「选信号最强的」凑合推送。** 推错到别人的屏上是不可撤销的外部动作，
  正确做法是拒绝并列出候选，让用户锁定地址。
